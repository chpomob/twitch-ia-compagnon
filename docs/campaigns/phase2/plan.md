## Decisions made by this plan (flagged so none is silent)

1. **Deadline convention — the R10 adoption rule, and how the executor and
   a module meet at the deadline.** A phase 2 provider computes
   `expiry = min(call.deadline, entered_at + spec.timeout_seconds)` from the
   `invocation.call`/`invocation.spec` it receives, on the module clock — the
   same arithmetic as `core/actions.py::_expiry` — and that value is the
   **only** deadline it knows. There is no lead, margin or early-stop
   quantity anywhere in `modules/audio_output/`, `modules/audio_input/` or
   `modules/stream_control/` (AC41): `stop_grace_seconds` is the
   terminate → kill interval that runs *after* the stop; the only two
   quantities subtracted from the deadline are the two AC41 authorizes by
   name, both in `audio.capture` — `grace_seconds`, R3's admission reserve
   of `capture_too_long`, evaluated once before any spawn, and the 1-s
   transcription reserve of R3's `skipped:deadline`, which bounds the
   optional transcription request's window only, never the recorder's
   kill (P11, round 2 P1, round 3 V4); a reconciliation read
   is bounded by `expiry − now` (the remaining time, not a constant).
   At `expiry` two things happen on the same clock instant: the module's
   own deadline watcher (a task parked on the injected sleeper until
   `expiry`) fires, and the executor's timer fires and cancels the
   provider task. Whichever runs first, the module performs **one** stop
   (terminate the player / kill the recorder — idempotent, a second trigger
   is a no-op) and returns its own interruption record; a `CancelledError`
   that reaches the provider coroutine during playback/capture is caught,
   the stop is issued if not yet issued, and the record is returned
   normally (the task ends with a *result*, not cancelled). The executor
   (P3) adopts that record on both paths: when the provider task wins
   `asyncio.wait` with a stamp `>= expires_at`, and when the timer wins and
   the cancelled provider task ends within `_cancel_grace` holding an
   interruption `ActionObservation`. A provider that never returns (neither
   path yields a record) is cut by the executor's timer with the generic
   record, exactly as in phase 1. **Status of the module's record:**
   `timeout` (cause `playback` for audio, code `capture_timed_out` for the
   recorder, `timeout` cause `confirmation_lost` for a scene/poll command
   already sent) when the stop was triggered by the module's watcher or by
   a `CancelledError` arriving at `clock() >= expiry` — the deadline is the
   interruption that actually happened; `cancelled` when the stop was
   triggered by the module's `drain()` hook or by a `CancelledError`
   arriving at `clock() < expiry`. The first trigger fixes the status; a
   later trigger changes nothing. **The transcription phase of
   `audio.capture` is outside this rule (round 2 P1; round 3 V1, V4):**
   once `attachments.put` has returned, the capture is complete (R3) and
   the module authors no interruption record. Its optional transcription
   request is bounded by the *transcription window*, the second of the
   two deadline subtractions AC41 authorizes, with these named
   quantities: `transcription_reserve = 1 s` (R3's `skipped:deadline`
   constant, the only literal), `transcription_edge = expiry −
   transcription_reserve`, and `transcription_window = transcription_edge
   − now`, read once after storing. The reserve exists for one reason
   only: phase 1 adopts a `success` only when its completion stamp is
   `< expires_at` (AC40), `core/actions.py::_observe` stamps the instant
   the invoke *actually* returns, and the module must wait for the
   optional transcription before it can author the capture's `success`
   record carrying its `audio_ref` — so it must return before `expiry`,
   never at it. Arithmetic and ordering, fixed: (1) `transcription_window
   ≤ 0` at entry → transcribe nothing, `transcription_status:
   "skipped:deadline"`, still `success`; (2) otherwise **attempt** — one
   request, bounded on the sleeper by `min(timeout_seconds,
   transcription_window)`; (3) **decide** at the wake, whatever woke it
   (the answer, the bound, `drain()`, a `CancelledError`): the module
   reads `now`; `now < transcription_edge` with an answer in hand → the
   answer's status (`ok` or its failure kind); otherwise the request is
   abandoned → `failed:stt_timed_out` — the clock decides, not which event
   won; (4) **author** the `success` record with its `audio_ref` and
   return with no further await. `_observe` stamps in the same task step
   as that return, so the stamp *is* the decision instant on the injected
   clock; the module's last scheduled wake is the edge, so a wake delayed
   past the edge by less than the reserve still stamps `< expiry` — the
   reserve is exactly the tolerance a delayed wake has, and the module
   never waits on anything scheduled at or after `expiry`. A wake delayed
   by the whole reserve is a loop stalled for a second, outside any
   module arithmetic (the stamp is the executor's); the phase 1 rule then
   treats the record as any late `success`, and the README records that
   limit beside the executor-cancellation one. The window bounds a
   request only — the recorder's kill stays at `expiry` exactly (AC39) —
   and applies to no other action: the audio write actions, the scene and
   poll paths stop, kill and read at `expiry` itself. A `CancelledError`
   or a `drain()` arriving in that phase abandons the request, never the
   capture. The two audio write actions call
   `invocation.mark_not_emitted()` at entry (playback is local, decision 4
   of the spec), so their `timeout`/`cancelled` survive the emission rule;
   the scene and poll commands call `mark_emitted()` before the command
   leaves, so their late `timeout` resolves `external_unknown` through the
   same rule, as R10 states. The executor's external-cancellation branch
   (`except CancelledError` in `_run_invocation`) is **not** changed: the
   coordinator's shutdown reaches a running playback or capture through
   the module's `drain()` hook (which issues the stop and lets the invoke
   return `cancelled` in time), so the module's record arrives on the
   ordinary provider path; changing the executor's own cancellation
   accounting is outside R10 and is recorded as a limit in the README.
2. **Player runner seam and output ownership (findings P2, P5).**
   `audio_output` drives the player through one injectable object:
   `start(argv) → process`, `write(process, chunk) → accepted bytes`
   (bounded 32 KiB writes on a blocking pipe), `close_stdin(process)`,
   `wait(process) → exit code`, `stop(process, grace_seconds)` (terminate
   now; kill after the grace on the injected sleeper if the player is
   still alive; counted as one *stop*, and one *kill* when escalated). The
   module writes the **complete WAV** — header and data chunk — and keeps
   the running total the runner reports; `accepted_data_bytes =
   min(data_bytes, max(0, accepted_total − data_offset))` with
   `data_offset` from `parse_wav` is the only quantity `played_ms` derives
   from. An output's slot is taken at `start(argv)` and released only when
   `wait(process)` has returned — by the call on a normal or failed exit,
   by the supervised escalation task after a stop (terminate →
   `stop_grace_seconds` → kill → `wait`). The interrupted call's
   observation is published as soon as its stop is issued (it never waits
   for the exit), and a queued successor's `start` happens only after the
   predecessor's `wait` returned, so two players never overlap on one
   output (AC4).

## Ordering rationale

Contracts before consumers: P1 (part vocabulary, capability and probe names)
changes `core/contracts.py`, which every later file imports; P2 makes the
executor enforce the audio lease before any provider produces one; P3 amends
the executor's adoption rule (R10) before any module relies on it — the three
new modules (P9, P10, P14, P16) return interruption records at the deadline
and would be cut to the generic record without it, so P3 precedes every
module step that tests a deadline through the real executor. P4 is an
independent core seam (service registry) needed by the platform modules
(P13) and `stream_control` (P16); it goes first so the shared harness (P5)
can build a registry by default. P5 upgrades the harness before the brain and
the modules change shape, because every new suite reads it. The brain follows
in two layers — the probe and capability name (P6), then the call-time
encoding, omission rule and estimate (P7) that need both the probe's verified
set and the executor's lease check. `audio_output` (P8, P9) needs contracts,
the harness and P3, and ships first among the modules because the delivery
proof (P17) and the scenario (P18) speak through it; `audio_input` (P10, P11)
needs the executor's audio lease (P2) and R10 (P3) and follows P8 so the
three `pyproject.toml` edits are serialised (P8 → P10 → P14). The proxy path
(P12) needs the vocabulary and the harness only and precedes the scenario.
The platform poll services (P13) precede `stream_control`'s scene step (P14)
and its polls step (P16), and P14 precedes the websocket provider (P15)
because the provider implements the boundary P14 defines; P16 follows P15 so
the two edits of `modules/stream_control/__init__.py` are ordered. P17 proves
R2 once the two delivery-capable modules exist and the brain's R4 hunks are
in; P18 integrates every module across both transports and must follow all
of them, P15 included (its scene-change shutdown case drives the websocket
provider). Profiles and the examples/profile suites (P19) need every module
and the scenario's seams; the README records the trials and the hygiene suite
greps the finished tree (P20). P21 is the full-branch gate: it reviews the
integrated set that no per-step review could see.

**Shared-file rule (finding P3).** Two steps that modify the same file are
ordered by an explicit dependency edge, so a dev loop never applies two
unordered edits to one file. The pairs and their edges: `core/contracts.py`
is P1 only; `core/actions.py` P2 → P3; `tests/test_observations.py` P1 → P2;
`tests/test_actions.py` P3 only; `tests/test_model_adapter.py` and
`modules/brain/__init__.py` P6 → P7; `modules/audio_output/*` and
`tests/test_audio_output.py` P8 → P9; `modules/audio_input/*` and
`tests/test_audio_input.py` P10 → P11; `pyproject.toml` P8 → P10 → P14;
`tests/test_stream_control.py` P4 → P13 → P14 → P15 → P16;
`modules/stream_control/__init__.py` P14 → P15 → P16; `docs/README.md`
P20 → P21; `tests/conftest.py` is P5 only, `tests/test_proxy.py` P12 only,
`tests/test_delivery.py` P17 only, `tests/test_phase2_scenario.py` P18 only,
the three profiles and `tests/test_examples.py`/`tests/test_profiles.py` P19
only, `tests/test_hygiene.py`/`tests/test_phase2_trials.py` P20 only. P18
names P15 directly; P19–P21 reach P15 through P18 → P16 → P15. The sequence
`P1..P21` satisfies every edge (each step depends on lower ids only).
