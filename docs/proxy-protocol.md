# Proxy protocol v1 — brain ⇄ PC agent over WebSocket JSON

**Status: normative.** This document fixes protocol v1 between the brain-side
`modules/proxy` (server, listens) and the agent-side `modules/agent_link`
(client, dials), as decided by the phase 1 specification (`docs/campaigns/
phase1/spec.md`, R6 and decisions 6–9) and the v2 design (`docs/design-v2.md`,
section 4.3). Where this document and the specification differ, the
specification wins and this document is wrong. Every frame type, error code,
`attachment_ack` code and close code below is spelled exactly as the constants
of `core/contracts.py` (section "Proxy protocol v1"); `tests/test_proxy.py`
checks that they do not drift apart.

Vocabulary: **brain** is the process running `modules/proxy`; **agent** is the
process running `modules/agent_link` together with the local capability
modules it exposes (`capture` in phase 1). The **bus is not distributed**: no
subscription, no trace and no run state crosses the wire; only action calls,
their observations, attachments, cancellations, a heartbeat and an allowlisted
event type do.

## 1. Transport

- One WebSocket connection per agent, opened by the agent towards
  `brain_url`. The agent works from behind NAT; the brain never dials.
- Exactly **one paired agent per brain** at any time (decision 6). A second
  agent authenticating while one is paired is refused (`agent_limit`, §7).
- Every **text frame** is one UTF-8 JSON object carrying the envelope of §2.
  A text frame that is not a JSON object, or whose envelope is malformed, is
  answered `error invalid_frame` (§7).
- **Binary frames** exist for one purpose only: the payload of an attachment,
  immediately after its `attachment` header (§10). A binary frame received at
  any other moment is answered `attachment_ack` with `accepted: false` and
  code `unexpected_binary`, and its bytes are discarded.
- TLS rules are in §14; the pairing token is in §4.

## 2. Envelope

Every text frame carries exactly these three fields at the top level, plus the
fields its type defines (§5):

| Field  | Type                | Rule |
| ------ | ------------------- | ---- |
| `v`    | integer             | Protocol version; **must be `1`** (`PROXY_PROTOCOL_VERSION`). Any other value, or a non-integer, is answered `error unsupported_protocol_version` and the connection is closed with code `4400`. |
| `type` | string              | One of the eleven text frame types of §5. An unknown `type` is answered `error unknown_frame`; the **connection is kept**. |
| `id`   | string, or `null`   | Correlation identifier (§3). `null` is legal **only** on an `error` frame that answers no identifiable frame. |

Unknown additional fields are ignored by the receiver (forward compatibility
within v1); a missing required field, or a field of the wrong type, is an
`invalid_frame`.

## 3. Correlation

Correlation is carried by `id` and depends on the frame's scope.

| Scope         | Frame types                                            | Value of `id` |
| ------------- | ------------------------------------------------------ | ------------- |
| Pairing       | `hello`                                                | An agent-generated, **non-empty string nonce**. A `hello` with a missing, non-string or empty `id` is answered `error invalid_frame` and the connection is closed `4400` (AC48). |
| Pairing       | `welcome`                                              | The **same `id` as the `hello` it answers** (the nonce), so the agent can match the reply to its own attempt. `welcome` additionally carries the server-issued `session_id`. |
| Session       | `ping`, `pong`, `event`, `attachment`, `attachment_ack` (`PROXY_SESSION_FRAME_TYPES`) | `id` = the current `session_id`. A session-scoped frame whose `id` differs from the current `session_id` is answered `error unknown_session` and **not processed** (a `ping` with `id: "other"` yields 0 `pong`). |
| Call          | `call`, `observation`, `cancel` (`PROXY_CALL_FRAME_TYPES`) | `id` = the `call_id` of the `ActionCall` (§5.4). |
| Answer        | `error`                                                | The `id` of the frame it answers, or **`null`** when none applies (e.g. an unparsable frame, or a `ping` received before any `hello`). |

`session_id` is a non-empty string generated by the brain for each successful
pairing and never reused for a later pairing of the same brain process. From
`welcome` on, it is the only accepted `id` for session-scoped frames until the
connection drops.

**Before `welcome` the brain accepts only `hello`.** Any other frame received
before pairing is answered `error unknown_session` (with `id: null`) and not
processed; the connection stays open so the agent can still send its `hello`
(AC48).

## 4. Pairing: `hello` / `welcome`

1. The agent sends `hello` with its `agent_id`, the pairing `token`, the
   `actions[]` it serves and its own `max_frame_bytes`.
2. The brain compares `token` with the configured pairing token **in constant
   time**. On mismatch it sends `error auth_failed` and closes `4401`; 0
   actions become ready (AC32).
3. If another agent is already paired, the brain sends `error agent_limit`
   and closes `4409`; the first agent stays connected (AC32).
4. Otherwise the brain compares each declared action against the spec it took
   from its catalog for the names of its `actions` allowlist (decision 7): the
   registry's discovered spec when an enabled manifest declares the action,
   else the declaration of a disabled module's manifest — `capture` on the
   server, where `screen.capture` is served remotely only. A declaration is
   **identical** when name, version, argument
   and result schemas, nature, supported destinations — and, being part of the
   compared spec, the optional `delivery` capability — are equal. An identical
   declaration makes that action **ready**; a differing one is excluded with
   `error action_mismatch` (`id` = the `hello` nonce) and leaves the others;
   a declared action absent from the allowlist is ignored.
5. The brain answers `welcome` carrying the nonce as `id`, the `session_id`,
   the accepted action names and its limits (§6). The agent resets its
   per-session state on every `welcome` (§8) and its backoff (§13).

Peer authentication grants nothing: a paired agent still executes every
`call` through its own default-deny executor (§9), and the brain still checks
its own authorization rules before issuing a `call`.

## 5. Frame types

Protocol v1 has **twelve frame types**: the eleven text frame types declared
by `PROXY_FRAME_TYPES`, plus the binary attachment frame. Direction "A→B" means
agent to brain, "B→A" brain to agent.

| `type`           | Direction | Scope   | Purpose |
| ---------------- | --------- | ------- | ------- |
| `hello`          | A→B       | pairing | Authenticate and declare served actions. |
| `welcome`        | B→A       | pairing | Accept the pairing, issue `session_id`, publish limits. |
| `error`          | both      | answer  | Refuse or fail a frame with a code. |
| `call`           | B→A       | call    | Forward an `ActionCall`. |
| `observation`    | A→B       | call    | Return the `ActionObservation` of a `call`. |
| `cancel`         | B→A       | call    | Best-effort cancellation of an in-flight `call`. |
| `attachment`     | A→B       | session | Header of an attachment transfer; followed by exactly one binary frame. |
| *(binary frame)* | A→B       | session | The attachment payload, exactly `size` bytes. |
| `attachment_ack` | B→A       | session | Accept or refuse the transfer. |
| `event`          | A→B       | session | An allowlisted event for the brain's local bus (§15). |
| `ping`           | both      | session | Heartbeat request (§12). |
| `pong`           | both      | session | Heartbeat answer. |

### 5.1 `hello` (agent → brain)

| Field             | Type            | Meaning |
| ----------------- | --------------- | ------- |
| `agent_id`        | non-empty string | Stable identifier of the agent; becomes `metadata.provider_id` of forwarded events (§15). |
| `token`           | string          | The pairing token. Never logged, never traced, never echoed. |
| `actions`         | array of objects | ActionSpec-shaped declarations: `name`, `version`, `description`, `argument_schema`, `result_schema`, `nature`, `required_permissions`, `supported_destinations` (objects `platform`, `channel_id`, `scope`), `timeout_seconds`, `idempotency`, and `delivery` when the action declares the delivery capability. |
| `max_frame_bytes` | positive integer | The largest text frame the agent accepts. |

### 5.2 `welcome` (brain → agent)

| Field        | Type             | Meaning |
| ------------ | ---------------- | ------- |
| `session_id` | non-empty string | Server-issued session identifier (§3). |
| `actions`    | array of strings | The accepted (ready) action names — a subset of the `hello` declaration. |
| `limits`     | object           | Brain limits, at least `max_frame_bytes` and `max_attachment_bytes`, plus `heartbeat_seconds` and `heartbeat_timeout_seconds` (§6, §12). |

### 5.3 `error` (either direction)

| Field       | Type    | Meaning |
| ----------- | ------- | ------- |
| `code`      | string  | One of the codes of §7 (`PROXY_ERROR_CODES`). |
| `message`   | string  | Human-readable, **sanitised**: never a token, a credential, a configured secret, a filesystem path nor the offending payload. |
| `retryable` | boolean | Whether the same frame may reasonably succeed later (§7). |

### 5.4 `call` (brain → agent)

The `ActionCall` fields of `core/contracts.py`, carried verbatim, plus the four
transport fields. `id` is the `call_id`.

| Field                 | Type             | Meaning |
| --------------------- | ---------------- | ------- |
| `action_name`, `action_version`, `arguments`, `conversation_id`, `run_id`, `call_id`, `source_event_id`, `principal`, `message_id`, `contract_version` | as `ActionCall` | Forwarded unchanged. `arguments` is a JSON object already validated by the brain's executor against the catalog spec; the agent's executor validates it again. |
| `destination`         | object           | `platform`, `channel_id`, `scope` — a concrete `Destination`. |
| `seq`                 | positive integer | Per-session sequence number, strictly increasing from `1` with the first `call` after `welcome` (§8). |
| `deadline_utc`        | string           | ISO-8601 UTC instant of the brain's deadline. **Informational only** (§9). |
| `remaining_ms`        | non-negative integer | Milliseconds left on the brain's monotonic clock when the frame was built. **This bounds the agent** (§9). |
| `max_attachment_bytes`| positive integer | The largest single attachment the brain accepts for this call (§6). |

The `ActionCall.deadline` monotonic float is **not** transported: it has no
meaning on another host. The agent rebuilds its own deadline from
`remaining_ms` (§9).

### 5.5 `observation` (agent → brain)

The `ActionObservation` fields: `status` (one of `TERMINAL_STATUSES`),
`provenance`, `result` (success only), `error` (`code`, `message`, optional
`retryable`; every non-success), `parts`. `id` is the `call_id`.

`parts` follow R4: `text` parts carry `text`; `image_ref` parts carry the seven
`IMAGE_REF_FIELDS` (`attachment_id`, `content_type`, `size`, `width`,
`height`, `captured_at`, `provider_id`) and **must name an attachment already
acknowledged `accepted: true` in this session** (§10). An `observation`
carrying an unacknowledged `attachment_id` is treated by the brain as an
`error` observation for that call (code `attachment_refused` of the brain
vocabulary). An observation never carries a filesystem path, a payload or an
inline image (AC33).

### 5.6 `cancel` (brain → agent)

No field beyond the envelope; `id` is the `call_id`. Best-effort: the agent
stops the call if it can, and its executor's own classification (§11) decides
the observation it returns, if any. The brain never waits for an answer.

### 5.7 `attachment` (agent → brain)

| Field           | Type             | Meaning |
| --------------- | ---------------- | ------- |
| `attachment_id` | non-empty string | Agent-chosen identifier, unique within the session. |
| `content_type`  | string           | One of `IMAGE_CONTENT_TYPES` (`image/png`, `image/jpeg`). |
| `size`          | positive integer | Exact byte length of the binary frame that follows. |
| `call_id`       | string, optional | The in-flight `call` the upload belongs to (§10). Absent: the most recently issued call still in flight. |

Followed by **exactly one binary frame** of `size` bytes (§10).

### 5.8 `attachment_ack` (brain → agent)

| Field           | Type             | Meaning |
| --------------- | ---------------- | ------- |
| `attachment_id` | string           | The header's identifier. |
| `accepted`      | boolean          | `true` when the bytes are stored under the run's lease. |
| `code`          | string, only when `accepted: false` | One of `ATTACHMENT_ACK_CODES`: `attachment_too_large`, `store_full`, `unexpected_binary`. |

### 5.9 `event` (agent → brain)

| Field        | Type   | Meaning |
| ------------ | ------ | ------- |
| `event_type` | string | Must be in the adapter allowlist (§15): `agent.status`. |
| `payload`    | object | Validated by the adapter for that type. |

Any `metadata` the frame carries is discarded and replaced by the adapter.

### 5.10 `ping` / `pong` (either direction)

No field beyond the envelope; `id` is the `session_id`. A `pong` answers a
`ping` with the same `id`.

## 6. Limits

| Limit                        | Applies to                       | Default (literal)           | Set by |
| ---------------------------- | -------------------------------- | --------------------------- | ------ |
| `max_frame_bytes`            | every text frame, both directions | `1048576` (`PROXY_DEFAULT_MAX_FRAME_BYTES`) | brain setting, agent setting; each side announces its own (`hello`, `welcome`). |
| binary bound                 | every binary frame               | `min(store max_object_bytes, max_attachment_bytes)` | brain: its attachment store's `max_object_bytes` and the proxy's `max_attachment_bytes`. |
| `max_attachment_bytes`       | one attachment                   | carried in every `call` and in `welcome.limits` | brain setting. |
| `max_entries`                | agent call table (§8)            | `1024`                      | agent setting. |
| `ttl_seconds`                | agent call table entries (§8)    | `300`                       | agent setting. |
| `heartbeat_seconds`          | interval between `ping`s (§12)   | `15`                        | both sides. |
| `heartbeat_timeout_seconds`  | wait for `pong` (§12)            | `10`                        | both sides. |

Rules:

- A text frame larger than the receiver's `max_frame_bytes` is answered
  `error frame_too_large` and the connection is closed `4413` (AC32: a
  `1048577`-byte text frame under the default). The size is measured on the
  UTF-8 encoded frame.
- A binary frame larger than the binary bound — or larger than the `size`
  announced by its header — is answered `error frame_too_large` and the
  connection is closed `4413`. The bound is applied **before** the bytes are
  buffered in full: the brain reads at most the bound then aborts.
- A header whose `size` exceeds `max_attachment_bytes` for the current call
  or the store's `max_object_bytes` is refused `attachment_ack` with
  `accepted: false`, code `attachment_too_large`, as soon as the header is
  read; the connection is kept and the header is forgotten. The agent must
  not send the payload of a refused header. Refusing a header does **not**
  relax the binary bound: a binary frame that nonetheless follows is handled
  exactly like one that no header announced — at or below the bound it is
  discarded without storing and refused `attachment_ack` `accepted: false`
  code `unexpected_binary` (connection kept); above the bound it is
  `error frame_too_large` with close `4413`, the brain reading at most the
  bound before aborting. Since a refused `size` is by definition above the
  bound, an agent that transmits the declared payload anyway is closed
  `4413`.
- Every setting above is finite and validated at startup; an omitted value
  takes the default, an invalid one fails `--check-config`.

## 7. Error codes and close codes

`code` values are the `PROXY_ERROR_CODES` constants. "Close" is the WebSocket
close code sent immediately after the `error` frame; "kept" means the
connection stays open.

| `code`                         | Sent by | `retryable` | Close   | When |
| ------------------------------ | ------- | ----------- | ------- | ---- |
| `auth_failed`                  | brain   | `false`     | `4401`  | `hello` token mismatch (constant-time comparison). |
| `agent_limit`                  | brain   | `true`      | `4409`  | A second authenticated agent while one is paired. |
| `unsupported_protocol_version` | both    | `false`     | `4400`  | `v` ≠ `1`. |
| `invalid_frame`                | both    | `false`     | `4400` for a malformed `hello`; kept otherwise | Not a JSON object, malformed envelope, missing/ill-typed field, `hello` with missing or empty `id`, `call` with missing or non-positive-integer `seq`, `call_id` retained under a different `seq` (§8). |
| `frame_too_large`              | both    | `false`     | `4413`  | Text frame above `max_frame_bytes`, binary frame above the binary bound (§6). |
| `unknown_frame`                | both    | `false`     | kept    | Unknown `type`. |
| `unknown_session`              | brain   | `false`     | kept    | Any non-`hello` frame before `welcome`; a session-scoped frame whose `id` ≠ current `session_id`. |
| `duplicate_call_unknown`       | agent   | `false`     | kept    | `call` with `seq ≤ last_seq` whose `call_id` is not retained (§8). |
| `action_mismatch`              | brain   | `false`     | kept    | A declared action differs from the catalog spec; that action is excluded, pairing continues. |
| `proxy_disconnected`           | brain (internally, as the observation of a `read`) | `true` | n/a | The connection dropped while the call was in flight (§11). |
| `event_not_allowed`            | brain   | `false`     | kept    | `event` with an `event_type` outside the allowlist (§15). |

Close codes (`PROXY_CLOSE_CODES`), in the application range 4000–4999:

| Close  | Constant                     | Meaning |
| ------ | ---------------------------- | ------- |
| `4400` | `PROXY_CLOSE_BAD_REQUEST`    | Unsupported protocol version, or invalid `hello`. |
| `4401` | `PROXY_CLOSE_AUTH_FAILED`    | Pairing token refused. |
| `4409` | `PROXY_CLOSE_AGENT_LIMIT`    | One agent per brain already paired. |
| `4413` | `PROXY_CLOSE_FRAME_TOO_LARGE`| Text or binary frame above its bound. |

A close code sent by the brain does not change the agent's reconnection
policy (§13): the agent keeps dialing with backoff for as long as it runs.
The `error` frame precedes the close so the agent can log the reason
(sanitised, §5.3).

## 8. `seq` and the agent's bounded call identity

The brain assigns `seq` per session: a positive integer, strictly increasing
from `1` with the first `call` after `welcome`. Nothing is retransmitted on
reconnect (§11); a repeated `call` on the same session comes only from the
brain re-sending an unanswered frame.

The agent keeps, per session, **bounded state: one integer plus the call
table**:

- `last_seq`: the highest `seq` accepted; `0` after `welcome`.
- the **call table**: at most `max_entries` (default `1024`) retained
  `(call_id → observation)` entries, each evicted after `ttl_seconds`
  (default `300`) on the agent's injected clock, or earlier when the oldest is
  displaced by a newer entry.

Both are **reset on every `welcome`**.

| Received `call`                                       | Rule |
| ----------------------------------------------------- | ---- |
| `seq > last_seq`                                      | New: executed through the agent's executor; `last_seq` becomes its `seq`; the observation is retained under its `call_id`. |
| `seq ≤ last_seq`, `call_id` retained                  | Returned from the table **without executing** (0 additional executions, AC36). |
| `seq ≤ last_seq`, `call_id` not retained (evicted or never seen) | Refused `error duplicate_call_unknown` (`retryable: false`), 0 executions. |
| `seq` missing or not a positive integer               | Refused `error invalid_frame`. |
| `call_id` retained under a different `seq`            | Refused `error invalid_frame`. |

An entry is retained from the moment the call is accepted (so a repeat
arriving while the first execution is still running waits for the same
observation rather than starting a second execution) until it expires. A
retained observation returned to a repeat is byte-identical to the one first
sent. After the table has evicted an entry, the agent can no longer prove the
call did not run: it refuses rather than guesses, and the brain's own
classification of the original call (§11) stands.

## 9. Deadlines

A `call` carries two time fields with different roles:

- `remaining_ms` **bounds** the agent: the call is executed with a deadline of
  `min(remaining_ms, the agent's own action timeout)` measured on the
  **agent's monotonic clock** from the moment the frame is received (AC34:
  `remaining_ms: 5000` → 5 s even with a wall clock 3 h off; `remaining_ms:
  20000` with `action_seconds: 10` → 10 s). The agent's own timeout is the
  executor's per-action timeout (`action_seconds` of its profile, or the
  spec's `timeout_seconds` when smaller).
- `deadline_utc` is **informational**: an ISO-8601 UTC instant for logs and
  diagnostics. It **never** extends a budget and is never used to compute the
  bound; wall-clock skew between the two hosts therefore cannot lengthen a
  call.

A budget is never renewed at a hop: the brain computes `remaining_ms` from its
own deadline, and the agent may only shorten it. When the brain's deadline
expires or the run is cancelled, the brain sends `cancel` best-effort (§5.6)
and resolves the call itself by the executor's classification (§11); a later
`observation` for that call is a late observation (§11).

## 10. Attachment transfer

Images travel **by reference**: the agent uploads the bytes into the brain's
attachment store under the run's lease, then names them from an `image_ref`
part. A transfer is exactly three steps (AC33):

1. **Header**: `attachment` (`attachment_id`, `content_type`, `size`) with
   `id` = `session_id`.
2. **Exactly one binary frame** of exactly `size` bytes. No other frame may be
   sent by the agent between the header and its binary frame. A binary frame
   without a preceding header, a second binary frame after a header, or a
   binary frame whose length differs from `size`, is refused `attachment_ack`
   `accepted: false` code `unexpected_binary` (length below `size`) or
   `error frame_too_large` with close `4413` (length above the binary bound,
   §6).
3. **Ack**: `attachment_ack` with `accepted: true`, or `accepted: false` and a
   code:
   - `attachment_too_large`: `size` above `max_attachment_bytes` or above the
     store's `max_object_bytes`. The refusal is sent on the header alone and
     the agent must not send the payload; if a binary frame follows anyway it
     is treated as unannounced (§6): discarded and refused `unexpected_binary`
     at or below the binary bound, `error frame_too_large` with close `4413`
     above it;
   - `store_full`: the store refused the object for any other bound
     (`max_objects`, `max_total_bytes`, `max_bytes_per_run`);
   - `unexpected_binary`: a binary frame that no header announced (including
     one sent after its header was refused), or a malformed pairing of header
     and payload.

Only an acknowledged `attachment_id` may appear in an `image_ref` part of a
later `observation` (§5.5). Stored bytes belong to the run named by the call
in flight and follow the store's lease and retention: they are released with
the run's cleanup exactly like a local provider's attachments.

**Call identity.** An upload is bound to exactly one call: the one the
header's `call_id` names, else the most recently issued call still in flight.
A header whose `call_id` names a call that is unknown or already terminal
(observed, cancelled, timed out, resolved on a drop) is refused
`unexpected_binary` on the header alone — it is never charged to another call
in flight. The binding is checked again when the binary frame arrives: a call
that ended between the header and its payload invalidates the header, and the
payload is refused `unexpected_binary` and discarded, so a late upload never
creates a lease after its run's cleanup. The agent
transfers before sending the `observation`, so a refused transfer lets it
return an `error` observation (`attachment_refused`) instead of a dangling
reference. Attachments are never retransmitted after a drop (§11).

## 11. Connection drops, classification and late observations

When the connection drops (transport close, heartbeat timeout §12, or the
brain stopping), the brain:

- marks every action served by the proxy **not ready** until a new
  `hello`/`welcome` succeeds; they are absent from the next authorized view
  the brain offers the model (AC35);
- resolves every in-flight call **by the nature of its action**, without any
  retransmission:
  - `write` → observation `external_unknown`, error cause
    `proxy_disconnected`: the effect may have left the agent and must not be
    replayed;
  - `read` → observation `error` with code `proxy_disconnected`,
    `retryable: true`: nothing external happened, the run continues with that
    observation.

The executor's own classification always stands over a transport hint: an
`observation` reporting `success` that arrives after the brain already
resolved the call is not merged back.

**Late observations.** An `observation` frame for a `call_id` that is already
terminal (resolved on a drop, timed out, cancelled, or already observed) or
unknown to the brain is **ignored** — it changes nothing — and counted in the
proxy's `late_observations` counter, +1 each (AC36). A second `observation`
for the same `call_id` is a late observation.

**Reconnection** re-pairs from scratch (§4): new `session_id`, `seq`
restarting at `1`, agent state reset (§8). The brain never re-sends the calls
it resolved on the drop; a run that needs the action again issues a new
`call` with a new `call_id`.

## 12. Heartbeat

Each side sends `ping` every `heartbeat_seconds` (default `15`) with `id` =
`session_id` and expects a `pong` with the same `id` within
`heartbeat_timeout_seconds` (default `10`). No `pong` in time is a **drop**:
the side that observed it closes the connection and applies §11 (brain) or
§13 (agent). A `pong` whose `id` is not the current `session_id` does not
count (§3). Heartbeats run on injected clocks in tests; no positive-duration
sleep is used to observe them.

## 13. Reconnection backoff (decision 9)

The agent dials `brain_url` for as long as it runs, with unlimited attempts:

- delay before attempt *n* (n ≥ 0 counting consecutive failures) is a **full
  jitter** draw: `rng() × min(cap, initial × multiplier^n)` with `initial` =
  `1` s, `multiplier` = `2`, `cap` = `30` s, `rng()` uniform in [0, 1) from the
  **injected RNG**;
- a `welcome` **resets** the failure count, so the next failure starts again
  from the 1 s base;
- a refused pairing (`4401`, `4409`, `4400`, `4413`) counts as a failure like
  a transport error.

With an RNG returning 0.5 the delays after six consecutive failures are exactly
`[0.5, 1.0, 2.0, 4.0, 8.0, 15.0]` s (AC37). The sleeper is injected; tests
never sleep.

## 14. TLS and validation rules

- The brain's `listen.host` may be non-loopback **only with `tls`
  configured** (certificate and key references, `${NAME}` style, no literal
  secret); a non-loopback listen without `tls` is **refused at validation**
  (`--check-config` exits 2, naming module and field, never a value).
- The agent's `brain_url` may be non-loopback **only with the `wss` scheme**;
  a non-loopback `ws://` URL is refused at validation the same way.
- Loopback (`127.0.0.1`, `::1`, `localhost`) may use plain `ws` — the
  two-process trial (AC39) runs on loopback.
- The pairing token is a credential: referenced as `${NAME}`, compared in
  constant time, redacted from traces and loss diagnostics like every
  configured secret. It never appears in an `error` `message`.

## 15. Event adapter allowlist

`event` frames reach the brain's local bus only through the proxy's **source
adapter**, which:

- accepts `event_type` ∈ {`agent.status`} only; any other type — including
  the supervision trace types (`module.*`, `input.*`, `brain.*`, `action.*`)
  and every `channel.*` type — is answered `error event_not_allowed` and
  publishes nothing (AC38);
- validates `payload` for the accepted type;
- sets `metadata.source = "proxy"` and `metadata.provider_id = agent_id` (the
  `hello` value) itself, whatever metadata the frame carried;
- publishes the resulting event on the local bus.

No `subscribe` call, no bus event and no trace ever crosses the transport in
either direction: the wire carries the twelve frame types of §5 and nothing
else.
